# 04. 수집·갱신 (ETL)

> **요약**
> - 원본은 **데이터 레이크**에 그대로 보관하고, 서빙 DB는 언제든 원본에서 다시 만든다. 그래서 다시 만들 때 API를 또 부를 필요가 없다.
> - 공공데이터 대부분은 변경분만 주는 API가 없다. **기준기간 단위로 해당 구간만 교체**하는 방식으로 증분 갱신한다.
> - 공공데이터포털은 초당 제한이 있어 **1건씩 약 0.9초 간격**으로 부른다. 전국 대량 적재는 운영계정 전환 후에 한다.

---

## 1. 저장 구조

```
data/lake/raw/{소스}/{수집일}/…gz    원본 그대로 (변경 금지)
data/lake/std/{테이블}/…             표준화 Parquet (UTF-8, WGS84, snake_case) — 후속
data/commerce.sqlite                서빙 DB (파일럿) → 이후 PostgreSQL+PostGIS
```

- 레이크는 지금 로컬 폴더(113MB). 이후 S3로 옮긴다 (기획서 D3, 2026-10-30 결정). 정제 계층은 Parquet, 학습은 DuckDB로 직접 읽는다.
- PostgreSQL은 앱·에이전트 조회용 **서빙**에 맞고, 원본 이력 보관은 레이크가 맡는다.

## 2. 소스별 갱신 방식

| 소스 | 제공 형태 | 갱신 방식 |
|---|---|---|
| 인허가 | CSV에 갱신구분(I/U/D)·갱신시점 컬럼 | **변경분만 반영**: 갱신시점 이후 행을 관리번호 기준으로 UPSERT |
| 상가정보 | 분기 전체 스냅샷 (`storeListByDate?key=20260630` = 분기 기준일만 응답) | 분기 스냅샷 적재 → 이전 분기와 비교해 신규·변경·폐업 계산 |
| 실거래 | 계약월 단위, 신고기한 30일·해제 신고로 과거 월이 바뀜 | 최근 3개월(시군구×월)을 매월 지우고 다시 적재 |
| 서울 상권분석 | 분기 | 최근 2개 분기 교체 |
| 생활인구·지하철 | 일 | 날짜별 추가, 늦게 반영되는 값 때문에 최근 7일 재적재 |
| R-ONE | 분기·연, 과거 값 수정 가능 | 통계표 단위 전체 교체 (작음) |
| 공정위·SGIS | 연 | 연도 단위 교체 |
| 법정동코드 | 현행 목록 | 전체 교체, 변경 이력은 `region_code_map` 유효기간으로 |
| 지적·공시지가·건물 (파일) | 월·연 전체 파일 | 스냅샷 단위 교체, 이력은 레이크에만 |
| 구매 데이터 (카드·통신) | 월 배치 파일 | 월 단위 추가 (계약 조건에 따름) |

공통 규칙: 모든 사실 테이블에 기준기간과 적재시각을 두고, "해당 기간 삭제 → 입력"을 한 트랜잭션으로 묶는다. 상가정보·건물처럼 스냅샷을 비교하는 소스는 변경 이력 테이블에 쌓아 개폐업 추세의 원천으로 쓴다.

## 3. API 이용 규칙 (실측으로 정한 것)

| 규칙 | 내용 |
|---|---|
| 초당 제한 | 공공데이터포털에 동시 4건을 보내면 429(초당 요청 초과)가 났다. 1건씩 0.9초 간격으로 697건을 오류 없이 처리했다 |
| 호출 상한 | 호스트별 상한을 두고 넘으면 그 단계만 멈춘다 (공공데이터포털 1,200 / R-ONE 600 / SGIS 200 / 브이월드 10 / 카카오 3,000) |
| 원본 저장 | 모든 응답을 `data/lake/raw`에 gzip으로 저장 |
| 키 보호 | 키는 `web/.env`에만 두고, 로그·오류 메시지에서 `***`로 가린다 |
| 일일 한도 | API별로 다르다. 공공데이터포털 마이페이지에서 확인. 운영계정 전환 신청 중 |

## 4. 운영계정 전환 후 할 일

| 작업 | 호출 수 | 소요 (0.9초 간격) |
|---|---|---|
| 상가정보 전국 (서울 제외 약 222만) | 약 2,240 | 약 35분 |
| 실거래 12개월 × 2종 (255개 시군구) | 약 6,120 | 약 1.5시간 |
| 이후 매월 실거래 증분 (최근 3개월) | 약 1,530 | 약 25분 |

실거래는 기존 DW의 2006~2024-06 이력(`rtms_trade` 등)과 필드를 맞춰 이어 붙인다.

## 5. 전국 확장 단계

| 단계 | 지역 | 근거 |
|---|---|---|
| 1 | 서울 (현재) | 공개 데이터가 가장 많음 |
| 2 | 경기·인천 | 수도권 통근 연계, 인천교통공사 승하차 파일 |
| 3 | 부산·대구·대전·광주·울산 | 지역 교통공사 데이터, 부산 생활인구 |
| 4 | 그 외 시군 | 공통 기반 + 추정 모델 |

단계마다 확인할 것: 점포 수 대조(상가정보 vs 인허가), 좌표 변환 정합, 추정치와 DW 실측의 오차, 기준월 최신성.

**서울 밖 매출·유동 공백 메우기 (구매 데이터 + 추정 모델)**
- 학습: 매출·유동이 있는 곳(서울 공개 데이터 + DW 2021~2024 전국 카드·유동)을 정답으로 쓴다. 입력은 전국 공통 특성만 쓴다(점포 구성, 인구, 지가, 건물, 교통, 개폐업).
- 보정: 서울 추정매출과 DW 신한 점포 매출을 서울에서 맞대어 비교해 보정계수를 만든다.
- 산출: 격자×업종 추정 매출·유동 지수와 신뢰등급(관측 / 보정 / 추정).

## 6. 스크립트 사용법

`web/` 폴더에서 실행한다. 키는 `web/.env` (형식: `web/.env.example`).

| 스크립트 | 하는 일 | 예시 |
|---|---|---|
| `etl/schema.sql` | 테이블 정의 | — |
| `etl/lib.ts` | 공통: 호스트별 간격·상한, 원본 저장, 키 가리기, 컬럼 자동 추가 | — |
| `etl/seoul-sqlite.ts` | 서울 전용 소스(상권영역·상권분석·생활인구·지하철·뷰) → `commerce.sqlite` | `npx tsx etl/seoul-sqlite.ts --only=seoul_quarterly` |
| `etl/nationwide-probe.ts` | 전국 소스(법정동·점포·상권영역·공정위·SGIS·R-ONE·인허가) → `commerce.sqlite`, 실측 기록 | `npx tsx etl/nationwide-probe.ts --only=sgis` |
| `etl/region-map.ts` | 지역 코드 대응표 생성 (SGIS 행정구역 목록 약 18 호출) | `npx tsx etl/region-map.ts` |
| `etl/industry-map.ts` | 업종 코드 대응표 생성·검증 (API 호출 없음) | `npx tsx etl/industry-map.ts` |
| `etl/store-file.ts` | 상가정보 시도별 CSV → `store`(최신, 전국) + `store_snapshot`(분기별 누적) | `npx tsx etl/store-file.ts data/raw/<폴더> 202609` |
| `etl/license-api.ts` | 인허가 업종 API(담배소매업·휴게음식점 …) → `license_event`. 이어 받기 가능, 오류 응답은 재시도 | `npx tsx etl/license-api.ts tobacco_retailers` |
| `etl/rone-area.ts` | R-ONE 임대동향 상권 이름 → 좌표 (`rone_area`, 카카오 키워드 약 500 호출) | `npx tsx etl/rone-area.ts` |
| `etl/gg-flowpop.ts` | 경기 유동인구 행정동 파일 → `gg_flowpop_dong_h`. **공공누리 2유형, 내부 심사 한정** ([10](10_데이터_이용조건.md)) | `npx tsx etl/gg-flowpop.ts "data/raw/<폴더>"` |
| `etl/bus-stops.ts` | 국토교통부 전국 버스정류장 파일(CP949) + 서울시 버스정류소 API(서울 보강, 겹침 제거) → `bus_stop` | `npx tsx etl/bus-stops.ts "data/raw/국토교통부_전국 버스정류장 위치정보_20261020.csv"` |
| `etl/subway-regions.ts` | 부산·대구·인천·광주·대전 교통공사 역별 승하차 파일(CP949, 형식 제각각) → `subway_station_stats` (역별 하루 평균·붐비는 시간). 이후 기간은 API로 갱신 예정 | `npx tsx etl/subway-regions.ts data/raw` |
| `etl/zone-stats.ts` | 상가정보 점포 × 소상공인 상권영역 → `zone_store_total`·`zone_store_scls`·`sido_scls_share` (유망 입지 찾기용, store 재적재 후 다시 실행, 약 20초) | `npx tsx etl/zone-stats.ts` |
| `etl/brand-alias.ts` | 공정위 등록명 ↔ 상가정보 상호 별칭 표 → `brand_member`·`brand_group`·`brand_alias` (API 호출 없음, 약 20초). 공정위·상가정보를 다시 적재한 뒤 실행. 수동 별칭은 파일 안 `MANUAL` 표, 실행 끝에 "가맹점은 많은데 상가정보 매칭이 적은 브랜드"를 찍어 준다 | `npx tsx etl/brand-alias.ts` |
| `etl/area-alias.ts` | 카카오 테마거리 전국(전국 사각형을 45곳 이하가 될 때까지 4등분, 약 230 호출) + 수동 별칭(`MANUAL`) → `area_alias`. 원본은 `data/lake/raw/kakao_theme` | `npx tsx etl/area-alias.ts` |
| `etl/indexes.ts` | 서빙 쿼리용 인덱스 (인허가 업종+좌표·날짜, R-ONE 상권명, 점포 시도명) + ANALYZE. **store·license_event·rone_stat을 다시 적재한 뒤 꼭 실행** (없으면 모니터링 1곳당 약 2초) | `npx tsx etl/indexes.ts` |
| `etl/merge-db.ts` | 2026-10-30 1회 병합에 쓴 스크립트. 지금은 실행하지 않는다 (`--force` 없이는 거부) | — |
| `etl/q.mjs` | 읽기 전용 조회 | `node etl/q.mjs ../data/commerce.sqlite "SELECT * FROM meta_source"` |
| `scripts/check-keys.ts` | 키 유효성 확인 | `npm run check:keys` |

주의: `store`, `rone`, `trade` 단계는 수백~수천 건을 호출한다. 한도를 확인하고 실행한다.
