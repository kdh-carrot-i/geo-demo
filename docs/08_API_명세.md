# 08. Agent API 명세와 모델 v0

마지막 갱신: 2026-10-30. 사용자용 설명은 [09_API_사용설명서](09_API_사용설명서.md)에 있다. Swagger 원본은 [web/server/openapi.yaml](../web/server/openapi.yaml)이다. 서버를 띄우면(`web`에서 `npm run dev:api`) `http://127.0.0.1:8787/api/docs`에서 볼 수 있다.

## 1. 서비스 컨셉 (2026-10-30 회의)

- 고객이 **카카오맵 로드뷰 이미지와 위치**를 올리면 **출자에 적합한 입지인지**를 점수로 보여 준다.
- 결과는 **의사결정 참고용**이다. 투자 판단을 대신하지 않으며 모든 수치에 출처와 신뢰등급을 붙인다.
- 제공 형태는 **Agent API**이고, Swagger를 함께 제공한다.

| | 내용 |
|---|---|
| 요청 | 좌표, 로드뷰 이미지, 상호명, 사업자번호, 주소. 여기에 **희망 업종**과 **매장 면적**을 추가해 권장 필드로 둔다 (3장) |
| 응답 | 점수, 매출 예측값, 지표, 리포트, 대화형 질의 |
| 전제 | **공공데이터만으로 동작**하게 설계한다. 기존 DW 데이터는 S3로 백업 중이고(~2024-06), 계약 연장은 논의 중이다. 쓸 수 있게 되면 정확도를 올리는 데 쓴다 (9장) |

## 2. 제공 가능 항목 (DW 없이, 현재 DB 실측 기준)

| 응답 항목 | 서울 | 전국 | 근거 | 신뢰등급 |
|---|---|---|---|---|
| **종합 점수** | ✅ | ✅ (음식점 업종) | 3년 생존 모델(전국 인허가 학습) + 세부 지표 백분위 | B |
| **3년 생존 확률** | ✅ | ✅ | 인허가 231만 건 (5장) | B (음식점만, 그 밖의 업종은 v1) |
| **매출 예측값** | ⚠ 범위로 제공 | ⚠ 범위로 제공 | 서울 상권×업종 추정매출로 학습. 처음 보는 위치에서는 오차가 큼 (6장) | C |
| 매출 벤치마크 (같은 상권·업종의 실제 평균) | ✅ | 🔧 서울 상권분석 같은 공개 집계가 없음 → 점포 카드매출 확보 시 (9장) | 서울 상권분석 | A |

## 4. 점수 정의 (score-v0.1, API 구현 때 적용)

```
종합 점수 = 생존 50% + 수요 15% + 경쟁 15% + 매출력 10% + 로드뷰 10%
```

| 항목 | 계산 | 범위 |
|---|---|---|
| 생존 | 3년 생존 확률의 전국 같은 업태 내 백분위 | 전국 (음식점) |
| 수요 | 유동 50% + 직장 25% + 상주 25%의 백분위. 전국은 SGIS 인구·직장인구로 대체 | 서울 / 전국 |
| 경쟁 | 100 − (유동인구 1만 명당 동일 업종 점포 수의 업종 내 백분위) | 서울 / 전국은 인구 대비 |
| 매출력 | 점포당 매출의 업종 내 백분위 | 서울만 (전국은 가중치를 나머지에 재배분) |
| 로드뷰 | PoC의 접근성·가시성·상업밀집도·시설현대화 평균 | 전국 |
| 등급 | A 상위 20% … E 하위 20% | |

**생존을 중심에 둔 이유 (백테스트 결과)**
- 처음에는 수요·경쟁·매출력·안정성·성장을 가중합한 규칙 점수(`ml/score_v0.py`)를 만들었다. 그런데 이 점수는 다음 3분기 상권 폐업률과 상관이 거의 없었다 (Spearman −0.02, 업종 내 중앙값 −0.04).
- 반면 생존 모델은 실제 폐업 여부를 학습하므로, 예측 하위 10%와 상위 10%의 실제 폐업률이 19%와 73%로 확실히 갈린다.
- 그래서 규칙 점수는 **설명용 세부 항목**으로만 남기고, 종합 점수의 중심은 생존 확률로 둔다.

**로드뷰 가중치를 10%로 둔 이유**: PoC 누적 55회에서 Claude와 로컬 VLM의 상권유형 일치율이 47%, 평균 점수 격차가 12.4점이었다. 같은 이미지를 두고도 엔진에 따라 판독이 크게 달라서, 보조 지표로만 쓴다.

## 5. 생존 모델 v0 (`ml/survival_v0.py`)

| 항목 | 내용 |
|---|---|
| 대상 | 전국 일반음식점 중 2018~2022년 인허가, 좌표 있음 (31.8만 건) |
| 레이블 | 인허가 후 3년 내 폐업 (시험 구간 폐업률 36%) |
| 변수 | 모두 **개업일 시점** 기준. 반경 300m·100m 영업 중 음식점 수, 같은 업태 수, 직전 12개월 개업·폐업 수와 회전율, 3~6년 전 개업한 주변 점포의 3년 폐업률, 업태, 시도, 면적, 다중이용 여부 |
| 분할 | 학습 2018~2020 / 검증 2021 상반기 / 시험 2021 하반기~2022 (시간 분할) |

| 버전 | 시험 AUC | 서울 AUC | 예측 하위 10% → 상위 10%의 실제 폐업률 |
|---|---|---|---|
| full (면적 포함) | **0.670** | 0.667 | 19% → 73% |
| location (위치·업태만) | 0.601 | 0.578 | 23% → 55% |

- 영향이 큰 변수: 매장 면적(52%), 주변 회전율(15%), 시도, 주변 과거 폐업률.
- 한계: 양도양수(주인 변경)도 폐업 후 신규 인허가로 잡혀서 실제 폐업보다 많이 집계된다. 그리고 v0는 음식점만 다룬다 (인허가 CSV를 일반음식점만 적재했기 때문). 휴게음식점(카페)·미용 등은 같은 방식으로 파일만 추가하면 확장할 수 있다.

## 6. 매출 예측 v0 (`ml/sales_v0.py`)

| 항목 | 내용 |
|---|---|
| 타깃 | 서울 상권×업종 분기 자료의 점포당 월 매출 (log). `thsmon_selng_amt`는 월 단위로 본다 (2026-10-30 결정) |
| 분할 | 상권 10%는 검증, 다른 10%는 시험(최신 분기)으로 떼어 둠. **시험 상권은 학습에 한 번도 나오지 않음** (신규 입지를 흉내 냄) |
| 기준선 | 같은 업종 중앙값 |

| 모델 | R²(log) | 오차율 중앙값 | ±30% 이내 | ±50% 이내 |
|---|---|---|---|---|
| 기준선 (업종 중앙값) | 0.285 | 63% | 23% | 40% |
| seoul (상권분석 변수 전부) | **0.348** | 59% | 25% | 43% |
| national (전국에서도 구할 수 있는 변수만) | 0.320 | 61% | 23% | 40% |

- 처음에 시간으로만 나눴을 때는 R² 0.70이 나왔다. 하지만 같은 상권이 학습과 시험에 모두 들어가 상권을 외운 결과였다. 상권 단위로 분리하자 0.35로 떨어졌다. **이 0.35가 신규 입지에 대한 실제 성능**이다.
- 결론: 공공데이터만으로는 신규 입지의 매출을 업종 평균보다 조금 나은 수준까지만 맞힌다. 그래서 API는 **p10~p90 범위와 신뢰등급 C**로 내보내고, 서울은 같은 상권의 실제 평균(벤치마크, 등급 A)을 함께 보여 준다.
- 정확도를 올리는 길은 카드 매출 같은 점포 단위 데이터다 (8장).

## 7. API 흐름

```
POST /v1/assessments ──202──▶ assessment_id
        │  (비동기 30~60초: 위치 확정 → 업종 확정 → 지표 집계 → 모델 → 로드뷰 판독 → 요약)
        ▼
GET  /v1/assessments/{id}?wait=30   점수·매출·지표·로드뷰·요약·출처
GET  /v1/assessments/{id}/report    html / pdf / json
POST /v1/assessments/{id}/messages  대화형 (SSE 스트리밍)
GET  /v1/coverage?lat=&lng=         위치별 제공 범위 (사전 확인, 무과금)
GET  /v1/industries?q=              업종 코드 검색
```

- 인증은 `X-API-Key` 헤더, 오류는 RFC 9457 `application/problem+json` 형식이다.
- 재시도에 대비해 `Idempotency-Key`를 받는다.
- 일부 단계가 실패하면 `status=partial`로 돌려주고 사유를 `warnings`에 적는다 (예: 로드뷰 수집 실패).
- 대화형은 [05_에이전트_설계](05_에이전트_설계.md)의 도구(경쟁점 목록, 매출 벤치마크 등)를 그대로 쓴다.

## 8. 인프라 (DW 대체안, 2026-10-30 결정)

```
원 API·파일 → S3 raw (.gz) → ETL → S3 정제 (Parquet)
                                   ├→ DuckDB/Python : 피처·학습 (ml/)
                                   └→ PostgreSQL+PostGIS : API 서빙 (반경 조회)
모델 파일(LightGBM)·평가 결과 → S3 models/{name}/{version}/
```

- **DW 없이** 공공데이터만으로 동작한다. 우리 규모(수천만 행)에서는 S3의 Parquet를 DuckDB로 직접 읽으면 충분하므로 BigQuery나 Athena는 쓰지 않는다. 필요해지면 Athena를 나중에 붙인다.
- 기존 DW 데이터는 S3로 백업 중이다 (2026-10-30). 정제 계층에 테이블로 추가하면 되고, 구조는 바뀌지 않는다.
- 결정 안건 D2(서빙 DB)는 PostgreSQL+PostGIS, D3(레이크)는 S3로 정리한다 ([01_기획서](01_기획서.md) 11장).

## 9. 구매 검토 (정확도를 올리려면)

| 부족한 것 | 영향 | 후보 (견적·약관 확인 필요) |
|---|---|---|
| 전국 유동인구 | 수요 점수와 매출 모델의 서울·전국 격차 | 통신사 유동인구 데이터 (SKT 지오비전 퍼즐, KT, LG U+) |
| 점포 단위 카드 매출 | 매출 예측이 신뢰등급 C에 머묾 | 카드사 데이터 (금융데이터거래소 등), 기존 신한·KB 재계약 |
| 배달 매출 | 배달 중심 업종 과소 추정 | 통신·배달 플랫폼 데이터 |

구매 결정 조건: **학습과 API 응답에 쓸 수 있는지**(재제공 범위), 갱신 주기, 공간 단위(격자·행정동).

**기존 DW 백업분 활용 (S3 백업 중, 계약 연장 논의 중)**
- 신한·KB 점포 카드매출(~2024-06)은 매출 모델의 **점포 단위 정답**이 될 수 있다. 지금 모델은 상권 평균만 학습해 신뢰등급이 C에 머물러 있다.
- 다만 데이터가 2024-06에서 끝나므로, 학습에 쓰더라도 최신 상권 변화는 공공데이터로 보정해야 한다.
- 먼저 확인할 것: 계약 종료 후에도 백업분을 학습에 쓸 수 있는지, 학습한 모델의 결과를 API로 외부에 제공해도 되는지.

## 11. 구현 현황 (v0, 2026-10-30)

### 실행

```
cd web
npm run dev:api                     # http://127.0.0.1:8787/api/docs (Swagger), 모델 워커는 자동 기동 (~15초)
npx tsx scripts/smoke-agent.ts      # 6개 시나리오 + 오류·리포트·대화 확인
```

`web/.env`에 `ANTHROPIC_API_KEY`가 있어야 로드뷰 판독·요약·대화가 동작한다. 없으면 그 단계만 건너뛰고 `status=partial`로 응답한다. `AGENT_API_KEYS`를 넣으면 `X-API-Key` 인증이 켜진다.

### 구조

### 심사 화면 (2026-10-30)

내부 심사역이 쓰는 화면이다. `npm run dev`를 실행한 뒤 `http://localhost:8000`을 연다. Swagger(`/api/docs`)와 같은 API를 쓰고, Swagger는 그대로 둔다.

| 단계 | 내용 |
|---|---|
| 1 위치 확인 | 주소·건물·상호 검색 (카카오) → 후보 선택 → 지도와 카카오 로드뷰로 **"이 주소가 맞나요?"** 확인. 지도를 눌러 위치를 옮길 수 있다. **"지금 화면 담기"**를 누르면 로드뷰를 브라우저 화면 공유로 캡처해 판독에 쓴다 (최대 4장). 사진 파일로 담는 방법도 있다 |
| 2 업종·조건 | 업종 자동완성, 면적, 반경, 상호, 사업자번호(하이픈 자동 제거), 관리 번호 |
| 3 결과 | 점수·등급, 항목별 막대와 근거, 월 매출 범위와 상권 평균, 경쟁 지표, 반경·경쟁점 지도, 시간대별 유동·생활인구, 요약·로드뷰 판독, 대화, 출처 |
| 지난 평가 | 목록 → 클릭하면 결과 화면 (`#/a/<평가ID>`로 공유 가능) |

- 코드는 `web/src/assess/`에 있다. 기존 지도 도구는 `#/map`으로 옮겼다.
- 로드뷰를 표시하려면 `web/.env`에 `KAKAO_JS_KEY`가 있어야 한다. 카카오 개발자 콘솔에서 같은 앱의 JavaScript 키를 쓰며, 등록 도메인은 localhost:8000이다.
- 브이월드가 회색 지도 이름을 `gray`에서 `white`로 바꿔서 프록시에서 이름을 바꿔 요청한다. 기존 지도 도구의 회색 지도도 이 수정으로 다시 나온다.

### 알려진 한계 (v0)

- **Claude 단계는 키가 없어 실제 호출을 검증하지 못했다.** 타입 검사만 통과한 상태다. 키를 넣고 스모크 테스트를 다시 돌려야 한다.
- 로드뷰 자동 수집(`roadview_auto`)은 아직 없다. 이미지를 첨부해야 한다.
- 임대료(R-ONE)·건물 정보는 아직 연결하지 않았다 (`null`).
- 매출 범위가 넓다 (p10~p90이 약 20배 차이). 중앙값보다 같은 상권 실제 평균(benchmark)이 더 믿을 만하다.
- 상권 매칭은 경계가 아니라 중심점과 면적으로 근사한다. 상권 경계 파일을 적재하면 정확해진다.

## 12. 2026-11-04~05 추가

### 12-1. 평가 결과 지표 (`indicators`)
- `resident_registry`: 주민등록 인구·세대 (필지 법정동, 월별, 1년 증감, 20~39세·60세+ 비율)

- `supply_pipeline`: 공사 중 상가·사무 면적 (반경 안 법정동, 건물별 최신 인허가), 1km 안 3년 내 입주 예정 세대
- `living_pop`: 서울은 250m 격자 합산, 부산 추가
- `competitors.franchise_share`, `competitors.nearest[].brand`: 상호 → 공정위 브랜드 별칭

### 12-2. 매출 예측 v1·v2 (사내 카드매출, 전국)
| | 정답 | 시험 (학습에 안 쓴 시군구) |
|---|---|---|
| v0 | 서울 상권 × 업종 평균 | 오차 중앙값 59%, ±30% 25% |
| v1 (`ml/sales_v1.py`) | KB 매장 월평균 (10개월) | 오차 중앙값 55%, ±30% 28%, R² 0.41 · 프랜차이즈 35% / 44% / 0.66 |
| v2 (`ml/sales_v2.py`) | 같음 + 면적·유동인구·신한·KCB·브랜드·입주 예정 | 오차 중앙값 53%, ±30% 29%, R² 0.46 · 프랜차이즈 34% / 45% / 0.71 · 면적 있는 매장 49% (2026-11-06) |

- `sales_forecast`: v2 모델 파일이 있으면 `model_version: "sales-v2"`, `variants.franchise`·`variants.independent`(각 `kb_card`·`total_est` p10/p50/p90), `conditions`(업종·층·면적·브랜드). 없으면 v0.
- 총매출 = KB카드 규모 × `calib_ratio`(서울 상권 비교 중앙값 2.0). 상권마다 차이가 커서 범위로만 해석.

### 12-3. 기타
- `GET /opportunities`: 성장(3년 내 입주 예정 세대) 10% 추가, `upcoming=true` 필터
