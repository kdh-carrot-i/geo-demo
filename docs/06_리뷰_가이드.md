## 2. 프로젝트 경위

1. **출발점**: 상용 GIS 프로그램(XRayMap)의 동작을 분석해 웹으로 옮기는 작업에서 시작했다. 좌표계·지도 기능을 참고했고, 라이선스·로그인·자체 서버 API는 제외했다. 지오코딩은 카카오, 필지 조회는 브이월드로 대체했다. 분석 결과(디컴파일 산출물)는 내부 참고용이며 배포하지 않는다.
2. **방향 전환**: 최종 목표를 상권 분석 AI Agent로 잡고 필요한 데이터와 확보 가능성을 조사했다.
3. **서울 DB → 전국 실측 → 병합**: 서울 공개 데이터로 DB를 만들고, 전국 확장 시 API로 어디까지 되는지 호출 한도를 지키며 측정한 뒤, 두 DB를 `data/commerce.sqlite`로 합쳤다.
4. **설계·기획**: 에이전트 구조와 기획서를 작성했다.

## 3. 핵심 결정과 근거

| 결정 | 근거 | 기각한 대안 |
|---|---|---|
| 지표 계산은 코드, LLM은 해석만 | 수치 재현성·검증 가능성 | 자유 SQL(text-to-SQL): 조인 오류·환각 위험 |
| 모든 도구 결과에 출처·기준시점·신뢰등급 | 데이터마다 시점·추정 여부가 달라 오해 위험 | 답변에서만 언급: 누락을 검증할 수 없음 |
| 파일럿 DB는 SQLite | 전국 기준 1.6GB, 단일 파일로 충분 | 처음부터 PostGIS: 인프라 결정(D2) 전 과투자 |
| 원본을 레이크에 보관 | 공공 API는 과거 데이터가 사라지기도 하고 호출 한도가 있음 | DB만 보관: 재처리 때 재호출 필요 |
| 기준기간 단위 교체로 증분 | 대부분 소스가 변경분 API를 주지 않음 (실측) | 매번 전체 재적재: 한도·시간 낭비 |
| 지적·건물은 파일 | 필지 약 3,900만 → API 4만+ 호출 | API 전량: 비현실적 |

## 4. 직접 확인하는 방법

`web/` 폴더에서 실행한다. 키는 `web/.env`에 있어야 한다(저장소에는 없음, `web/.env.example` 참고).

| 확인할 것 | 명령 | 기대 결과 |
|---|---|---|
| 테이블별 출처·기준시점·상태 | `node etl/q.mjs ../data/commerce.sqlite "SELECT table_name, status, row_count, std_period FROM meta_source"` | [03_DB_설계](03_DB_설계.md) 2장과 같은 행 수 |
| 전국 실측 결과 | `node etl/q.mjs ../data/commerce.sqlite "SELECT source, scope, total_rows, calls_full, verdict FROM api_feasibility"` | [02](02_데이터_확보현황.md) 3장과 같은 수치 |
| 서울 상권 커피 점포당 매출 상위 | `node etl/q.mjs ../data/commerce.sqlite "SELECT trdar_cd_nm, stor_co, sales_per_store FROM v_ta_competition_latest WHERE svc_induty_cd_nm='커피-음료' ORDER BY sales_per_store DESC LIMIT 10"` | 2026Q2 상위 10개 상권 |
| 강남구 음식점 개업·폐업 추이 | `node etl/q.mjs ../data/commerce.sqlite "SELECT yr, opened, closed FROM v_food_license_flow_y WHERE sgg_nm='강남구' AND yr>='2023'"` | 2025년부터 폐업이 개업보다 많음 |
| API 키 유효성 | `npm run check:keys` | 항목별 OK (키는 `***`로 가려짐) |

> 주의: ETL 재실행은 공공 API 호출 한도를 쓴다. 리뷰 목적이라면 위의 조회만 하고 적재 스크립트는 실행하지 않는다.

## 7. 데이터·ML 프로파일 (인프라·플랫폼 검토용)

> 공간 정보가 붙은 **정형·시계열 데이터**를, 학습 기준 **수백만~수천만 행**(원천은 1억 행 이상 가능) 규모로, **SQL + Python**으로 전처리해, **매출 추정(회귀)과 폐업 예측(분류)**을 하는 프로젝트다.

### 7-1. 데이터 유형 — 주: 일반 정형 / 부: 시계열 수치

| 구분 | 데이터 |
|---|---|
| 일반 정형 (주) | 점포 목록, 인허가(개업·폐업), 실거래, 법정동·행정동·업종 코드, 공정위 브랜드 정보 |
| 시계열 수치 (부) | 상권별 분기 매출·점포수, 월별 카드매출(DW), 일·시간대 생활인구, 지하철 승하차 |
| 공간 데이터 | 좌표, 상권·필지 폴리곤. 반경·포함 관계 계산이 많다 |
| 해당 없음 | 센서·설비 데이터 없음. 로그·이벤트는 인허가 개폐업 이력 정도 (에이전트 대화 로그는 이후) |

### 7-2. 데이터 규모 — 학습 기준 수백만~수천만 행, 원천은 1억 행 이상 가능

| 범위 | 규모 |
|---|---|
| 현재 파일럿 DB | 큰 표가 수십만~수백만 행 (인허가 231만, 서울 상권 점포 61만, 서울 점포 55만). 전체 1.6GB |
| 전국 공공데이터 | 점포 277만 × 분기 누적, 필지 약 3,900만, 건물 약 700만 → 수백만~수천만 |
| DW 구매 데이터 | 점포×월 카드매출(2021~2024), 셀×시간 유동인구 → 1억 행 이상 가능성. **실제 행 수 확인 필요** |

### 7-3. ML 계획 — 주: 예측 모델(회귀·분류) / 부: 시계열 예측

| 유형 | 용도 | 우선순위 |
|---|---|---|
| 회귀 | 서울 밖·점포 단위 매출 추정 (구매 데이터 공백 보완), 유동인구 추정 | 1 |
| 분류 | 폐업 위험 예측 (기존 DW `store_closure`와 같은 문제) | 1 |
| 시계열 예측 | 상권 매출·점포수 추세 (뜨는/지는 상권) | 2 |
| 이상 탐지 | 데이터 품질 점검 정도 | 낮음 |
| 딥러닝 | 계획 없음. 정형 데이터라 트리 기반 모델(LightGBM 등)로 시작 | 낮음 |

에이전트의 대화·해석은 Claude API를 쓴다. 직접 학습하는 모델은 위의 수치 예측 모델이다.

### 7-4. 전처리 — SQL(대량 Join·집계·공간 계산) + Python(피처·학습)

| 단계 | 방식 |
|---|---|
| 현재 | TypeScript ETL로 수집·적재, SQLite의 SQL·뷰로 집계 |
| 권장 | 수천만 행 Join·집계·공간 계산은 DB 안에서 SQL로, 피처 엔지니어링·학습은 Python으로 |
| SQL 엔진 | DuckDB (S3 Parquet 직접 조회) + PostgreSQL (서빙). 2026-10-30 결정 |

### 7-5. 권장 데이터 흐름

2026-10-30 결정: **DW 없이 S3 중심**으로 간다. 기존 DW가 인프라에 들어올지 불확실하기 때문이다.

```
원 API·파일 → S3 raw → ETL → S3 정제(Parquet) ─ DuckDB/Python → ML → 모델 (S3 models/)
                                       ↓ 요약본·예측값·점수
                             PostgreSQL+PostGIS (서빙) → Agent API·지도
```

- **S3 + DuckDB가 가운데**: 수천만 행 규모에서는 Parquet를 DuckDB로 직접 읽어도 충분하다. 별도 DW 비용이 없고, 커지면 Athena를 붙인다.
- **PostgreSQL은 뒤(서빙)**: API의 반경 질의는 응답이 빨라야 하고 질의마다 비용이 들면 안 된다. 요약본만 내려 쓴다.
- **구매 데이터**: DW가 들어오거나 새로 구매하면 S3 정제 계층에 테이블로 추가한다. 구조는 바뀌지 않는다.
- 이전 안(레이크 GCS → BigQuery)은 DW가 BigQuery에 남는다는 전제였으나 폐기했다.

### 7-6. 확인이 필요한 것

| 항목 | 이유 | 확인할 곳 |
|---|---|---|
| DW 주요 테이블 행 수 (카드매출, 유동인구) | 규모 답변(7-2)과 인프라 선택을 가장 크게 바꾼다 | DW 담당자 |
| DW가 인프라에 들어오는지 | 들어오면 구매 데이터를 S3에 추가 (구조는 그대로) | DW 담당자 |
