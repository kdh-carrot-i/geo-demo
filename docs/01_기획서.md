# 상권 경쟁력 분석 AI Agent — 프로젝트 기획서 (v0.1)

작성일 2026-10-30 · 상태: 파일럿 착수 전 검토용 · 근거 문서: 이 폴더의 02~07

---

## 1. 한 줄 요약

공공데이터와 보유 유료 데이터를 하나의 상권 DB로 묶고, 그 위에서 **"이 자리에서 이 업종을 하면 경쟁력이 있는가"**에 근거와 함께 답하는 AI Agent를 만든다. 먼저 서울에서 파일럿으로 검증하고 전국으로 넓힌다.

## 2. 배경

- 소상공인365·오픈업·빅밸류 같은 서비스는 지도와 지표를 보여 주지만, **질문에 맞춰 근거를 엮어 판단해 주는 기능**은 약하다.
- 우리에게는 2021~2024년 카드 매출·통신 유동인구·KCB 데이터(기존 DW)가 있지만 갱신이 멈춰 있고 서비스에 연결되어 있지 않다.
- 공개 데이터만으로도 경쟁점·인구·비용·개폐업은 전국 단위로 확보할 수 있다는 것을 실측으로 확인했다(`140_nationwide_api_probe.md`). **매출과 유동인구는 서울 밖에서는 유료 데이터나 추정 모델이 필요하다.**

## 3. 목표

| 구분 | 목표 |
|---|---|
| 파일럿 (서울) | 상권·업종 단위로 경쟁점, 수요, 매출, 비용, 트렌드를 근거와 함께 답하는 에이전트 데모 |
| 1차 확장 (전국) | 공통 기반(점포·인허가·인구·비용·프랜차이즈)으로 전국 질의에 답하고, 데이터 한계를 명시 |
| 2차 확장 | 유료 데이터 갱신 + 추정 모델로 전국 매출·유동 공백을 메우고 신뢰등급 표시 |

**하지 않는 것 (파일럿 범위 밖)**
- 투자·창업 권유나 확정적 판단. 근거와 지표를 제시하고 판단은 사용자가 한다.
- 개인 단위 데이터. 사업장·집계 단위만 다룬다.
- 크롤링 데이터. 공식 API·파일·계약 데이터만 사용한다.

## 4. 사용자와 대표 질문

| 사용자 | 대표 질문 |
|---|---|
| 예비 창업자 상담 담당 | "성수역 500m 안에서 카페를 하면 경쟁이 얼마나 치열한가? 비슷한 상권과 비교하면?" |
| 프랜차이즈 점포개발 | "이 브랜드가 아직 없는 서울 상권 중 유동인구 대비 동종 점포가 적은 곳은?" |
| 내부 분석가 | "최근 1년 개업 대비 폐업이 많은 업종·지역은? 근거 데이터와 기준 시점은?" |

## 5. 해결 방식

```
질문 → AI Agent(Claude) → 도메인 도구 9개 → 상권 DB → 근거가 붙은 답변 + 지도 + 리포트
```

- **숫자는 도구가, 해석은 모델이**: 지표 계산은 정해진 코드가 하고, 모델은 필요한 도구를 고르고 결과를 설명한다. 수치 환각을 막고 결과를 재현할 수 있다.
- **모든 수치에 출처와 기준 시점**: 예) "서울 상권분석 추정매출, 2026년 2분기". 추정치는 추정이라고 표시하고 신뢰등급(A/B/C)을 붙인다.
- **데이터가 없으면 없다고 말한다**: 서울 밖 매출처럼 확보되지 않은 항목은 이유와 함께 "없음"으로 답한다.

상세: [05_에이전트_설계](05_에이전트_설계.md)

## 6. 데이터 전략

### 6.1 확보 현황 (2026-10-30 실측)

| 영역 | 서울 | 전국 | 출처 |
|---|---|---|---|
| 경쟁점 (점포·업종·위치) | ✅ 55만 | ✅ 277만 (API, 분할 적재 예정) | 소상공인 상가정보 |
| 개폐업 이력 | ✅ | ✅ 일반음식점 231만 (영업 중 69만) | 지방행정 인허가 |
| 프랜차이즈 (가맹점수·평균매출·창업비) | ✅ | ✅ 3개년 | 공정위 |
| 거주·직장 인구 | ✅ 상권 단위 | ✅ 행정동 3,559 | 서울 상권분석, SGIS |
| 유동인구 | ✅ 상권·행정동 | ❌ → 유료(통신) | 서울 생활인구, (LG U+ DW ~2024-05) |
| 매출 | ✅ 상권×업종 | ❌ → 유료(카드) + 추정 모델 | 서울 추정매출, (신한·KB DW ~2024-06) |
| 임대료·공실·권리금 | ✅ | ✅ (R-ONE 지역·상권) | 한국부동산원 |
| 거래가 | ✅ | ✅ (실거래 API) | 국토부 |
| 필지·건물 | 단건 API | 📁 파일 | 브이월드, 세움터 |
| 검색 관심도 | ⏸ | ⏸ | 네이버 (플랫폼 이관 중) |

### 6.2 저장 구조
- **데이터 레이크**(원본 그대로 보관) → **표준화 계층**(Parquet) → **서빙 DB**(파일럿 SQLite → PostgreSQL+PostGIS).
- 원본을 보관해 두기 때문에 서빙 DB는 API 재호출 없이 언제든 다시 만들 수 있다.

### 6.3 갱신 (증분) 방식
- 공공데이터 대부분은 변경분만 주는 API가 없다. 대신 **기준기간 단위로 해당 구간만 교체**한다. 실거래는 최근 3개월, 상권은 최근 2분기, 생활인구는 일자별로 교체한다.
- 인허가는 갱신구분(I/U/D) 컬럼이 있어 진짜 증분이 가능하다.
- 상가정보는 분기 전체 스냅샷이다. 이전 분기와 비교해 신규·폐업을 직접 계산하고, 이것이 개폐업 추세 지표가 된다.

## 10. 리스크와 대응

| 리스크 | 영향 | 대응 |
|---|---|---|
| 서울 밖 매출·유동 데이터 공백 | 전국 답변의 깊이 부족 | 유료 데이터 재계약 + 추정 모델, 신뢰등급으로 한계 명시 |
| 유료 데이터 이용 범위 | AI 학습·서비스 제공 불가 시 사용 제한 | 계약에 학습·파생지표 제공 범위 명시 전까지 에이전트에 연결하지 않음 |
| 공공 API 호출 한도 | 전국 적재 지연 | 운영계정 전환, 대량은 파일, 호출 간격 제어(구현 완료) |
| 지역 코드 체계 변경 (광주·전남 통합 등) | 시계열 단절, 조인 오류 | 유효기간을 가진 코드 크로스워크 |
| 업종 분류 불일치 (상가정보 247 ↔ 서울 100 ↔ 공정위) | 업종별 비교 오류 | 크로스워크 + 분석가 검수 (P0) |
| LLM 오답·과신 | 신뢰 하락 | 결정적 도구, 출처 강제, 골든셋 회귀 평가 |
| 보안 (키·자격증명) | 유출 | 서버 측 보관, 로그 마스킹. 기존 DW 문서의 평문 자격증명은 교체 필요 (security.md S11) |
