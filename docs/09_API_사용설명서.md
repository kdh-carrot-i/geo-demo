# 09. Agent API 사용설명서 (v0)

이 문서는 **API를 호출하는 개발자와 결과를 읽는 기획·심사 담당자**를 위한 것이다. 설계 배경은 [08_API_명세](08_API_명세.md)에 있다.

- 화면으로 보기: 서버 실행 후 `http://127.0.0.1:8787/api/docs` (Swagger). 요청과 응답 예시가 들어 있다.
- 명세 원본: [web/server/openapi.yaml](../web/server/openapi.yaml)

## 1. 이 API가 하는 일

위치(좌표 또는 주소)와 업종, 로드뷰 이미지를 보내면 다음을 돌려준다.

- **출점 적합도 점수** (0~100, A~E 등급)
- **3년 생존 확률** (음식점 업종)
- **월 매출 예상 범위** (서울)
- 주변 경쟁점, 인구 같은 근거 지표와 출처
- 요약, 리포트, 후속 질문에 대한 답변

결과는 **의사결정 참고 자료**다. 투자나 출자 판단을 대신하지 않는다.

## 2. 빠른 시작 (3단계)

**① 평가 요청** → `assessment_id`를 받는다 (`202`)

```bash
curl -X POST http://127.0.0.1:8787/api/v1/assessments \
  -H "X-API-Key: <발급받은 키>" -H "content-type: application/json" \
  --data-binary @request.json
```

`request.json` 예시:

```json
{ "lat": 37.5663, "lng": 126.9779, "industry": "한식", "floor_area_m2": 66, "store_name": "OO식당" }
```

> Windows 터미널에서 한글을 명령줄에 직접 쓰면 깨질 수 있다. 위처럼 **UTF-8로 저장한 파일**을 `--data-binary @파일`로 보낸다.

로드뷰 이미지까지 보낼 때는 multipart를 쓴다:

```bash
curl -X POST http://127.0.0.1:8787/api/v1/assessments -H "X-API-Key: <키>" \
  -F lat=37.5663 -F lng=126.9779 -F industry=I20101 -F floor_area_m2=66 \
  -F roadview_images=@front.jpg -F roadview_images=@side.jpg
```

**② 결과 받기** — `wait=60`이면 끝날 때까지 최대 60초 기다렸다가 응답한다

```bash
curl "http://127.0.0.1:8787/api/v1/assessments/<assessment_id>?wait=60" -H "X-API-Key: <키>"
```

`status`가 `done` 또는 `partial`이면 완료된 것이다. `queued`나 `running`이면 다시 조회한다.

**③ 리포트 보기 / 질문하기**

```bash
# 브라우저로 열어 인쇄하면 PDF로 저장할 수 있다
http://127.0.0.1:8787/api/v1/assessments/<assessment_id>/report

curl -X POST http://127.0.0.1:8787/api/v1/assessments/<assessment_id>/messages \
  -H "X-API-Key: <키>" -H "content-type: application/json" --data-binary @question.json
# question.json: { "message": "근처 경쟁점이 많은 편인가요?" }
```

## 3. 요청 항목

| 항목 | 필수 | 설명 |
|---|---|---|
| `lat`, `lng` | 좌표 또는 주소 중 하나 | WGS84 위경도 |
| `address` | 〃 | 도로명 또는 지번 주소 |
| `industry` | 권장 | 희망 업종. 이름(예: "카페")이나 코드(예: `I21201`). 코드는 `GET /v1/industries?q=` 로 찾는다 |
| `floor_area_m2` | 권장 | 예정 매장 면적(㎡). 생존 예측 정확도가 크게 오른다 |
| `roadview_images` | 선택 | 카카오맵 로드뷰 캡처. 최대 4장, 장당 5MB, JPG·PNG·WebP |
| `store_name` | 선택 | 상호. 프랜차이즈 판별과 업종 추정에 쓴다 |
| `biz_no` | 선택 | 사업자등록번호 10자리 (하이픈 없이). 영업 상태 확인에만 쓴다 |
| `radius_m` | 선택 | 경쟁점 집계 반경. 100 / **300**(기본) / 500 / 1000 |
| `client_ref` | 선택 | 호출하는 쪽의 관리 번호. 결과에 그대로 돌려준다 |

## 4. 결과 읽는 법

| 볼 곳 | 뜻 |
|---|---|
| `score.total`, `score.grade` | 종합 점수와 등급. A ≥ 80, B ≥ 60, C ≥ 40, D ≥ 20, E < 20 |
| `score.components[]` | 점수를 이루는 항목(생존 50%, 수요 15%, 경쟁 15%, 매출력 10%, 로드뷰 10%). 각 항목의 `basis`에 근거가 문장으로 적혀 있다 |
| `score.survival_3y_prob` | 지금 이 자리에 이 업종으로 개업했을 때 3년 뒤에도 영업하고 있을 확률 |
| `score.evidence_weight` | 데이터가 있었던 항목의 가중치 합. 1이면 모든 항목에 근거가 있다는 뜻이다. 빠진 항목의 가중치는 나머지 항목에 나눠 준다 |
| `sales_forecast.p10 ~ p90` | 점포당 **월** 매출 예상 범위. 오차가 크므로 범위로 읽는다 |
| `sales_forecast.benchmark` | 같은 상권, 같은 업종의 **실제** 점포당 평균 매출. 예측값보다 이 값이 더 믿을 만하다 |
| `indicators` | 경쟁점, 유동·생활·상주·직장인구, 음식점 개폐업, 공시지가 |
| `summary` | 한 줄 결론, 기회, 리스크, 현장에서 확인할 것 |
| `confidence` (A/B/C) | **A** 실측·공식 통계 / **B** 실측 기반 계산·검증된 모델 / **C** 오차가 큰 추정 |
| `provenance` | 사용한 데이터의 출처와 기준 시점 |
| `warnings` | 빠졌거나 근사한 항목과 그 이유 |
| `status = partial` | 일부 단계가 빠졌다 (예: 로드뷰 판독 실패). 이유는 `warnings`에 있다 |

**등급 제한**: 생존 모델이 없거나(음식점 외 업종) 근거가 부족하면(`evidence_weight` < 0.75) 점수가 높아도 **최대 B**로 표시한다. 근거가 30% 미만이면(예: 업종 미확정) 등급을 매기지 않는다(`grade: null`). 실제 사례는 [5장](#5-입력-예시와-결과).

### 4-1. 판단 근거 읽는 법 (`score.explanation`)

심사 화면의 점수 카드 아래 "판단 근거"에 같은 내용이 나온다. 예: 서울 시청 앞 한식 66㎡

| 필드 | 예시 | 뜻 |
|---|---|---|
| `grade_reason` | 38.6점은 20~40점 구간이라 D(주의)다. | 등급이 정해진 이유. 등급을 제한하거나 보류했다면 그 이유도 적힌다 |
| `formula` | (24.6×50% + 48.4×15% + 35.7×15% + 98.3×10%) ÷ 90% = 38.6점 | 종합 점수 계산식. 빠진 항목(로드뷰 10%)이 있으면 남은 가중치 합(90%)으로 나눈다 |
| `drags` | 3년 생존 25점 (가중치 50%, 종합 점수를 −14.1점 움직임) — … | 종합 점수를 가장 많이 **내린** 항목 (최대 2개) |
| `lifts` | 매출력 98점 (가중치 10%, 종합 점수를 +5.4점 움직임) — … | 가장 많이 **올린** 항목 (최대 2개) |
| `missing` | 로드뷰 (가중치 10%) — 로드뷰를 담지 않아 … | 데이터가 없어 빠진 항목과 이유 |
| `rules` | 가중치, 등급 구간, 등급 제한 규칙 | 모든 평가에 공통인 규칙 |

"움직임"은 그 항목이 50점(비교 대상의 중간)에서 얼마나 떨어져 있는지에 가중치를 곱한 값이다. 예: 3년 생존 24.6점 → (24.6 − 50) × 50% ÷ 90% = −14.1점.

### 4-2. 점수 항목별 설명 (`score.components[]`)

| 필드 | 뜻 |
|---|---|
| `reason` | 이 값이 나온 이유 한 문장. 예: "같은 업종이 서울 평균보다 29% 더 몰려 있어 35.7점이다." |
| `method` | 계산 방법 |
| `inputs[]` | 계산에 쓴 숫자. 예: 경쟁 강도 → 반경 300m 같은 업종 73곳, 전체 1,189곳, 반경 안 비중 6.1%, 서울 비중 4.77%, LQ 1.29 |
| `sources[]`, `inputs[].source` | 그 숫자의 출처. `provenance[].key`와 같은 값 |

| 항목 | 가중치 | 계산 | 50점의 뜻 |
|---|---|---|---|
| 3년 생존 | 50% | 생존 모델이 낸 3년 내 폐업 확률을 같은 업태 신규 개업들과 비교해, 이 자리보다 폐업 위험이 높은 곳의 비율 | 같은 업태 신규 개업의 중간 |
| 수요 | 15% | 서울: 유동 50% + 직장 25% + 상주 25%의 서울 상권 내 백분위. 서울 밖: 행정동 인구 50% + 종사자 50%의 전국 백분위 | 서울 상권(또는 전국 행정동)의 중간 |
| 경쟁 강도 | 15% | 100 − 50 × 입지계수(반경 안 같은 업종 비중 ÷ 같은 시도 전체 같은 업종 비중) | 그 시도 평균만큼 밀집 |
| 매출력 | 10% | 이 상권 같은 업종 점포당 월 매출의 서울 상권 내 백분위 | 서울 상권의 중간 |
| 로드뷰 | 10% | Claude 판독 5개 항목(보행 유동·접근성·가시성·상업 밀집·시설 상태) 평균 | 보통 |

### 4-3. 데이터 출처 (`provenance[]`)

응답의 `provenance`에는 그 평가에 **실제로 쓴 출처만** 고정된 순서로 들어간다. 심사 화면의 [번호]는 이 순서(1부터)다. 지표마다 `sources`로 어느 출처에서 왔는지 표시한다.

수요 지표의 출처는 다음과 같다.

| 화면 지표 | 제공 기관 | API (서비스명) | 사용한 값 | 기준 |
|---|---|---|---|---|
| 유동인구 (분기 합계), 2030·주말 비중, 시간대 비중 | 서울시 (서울 열린데이터광장) | `openapi.seoul.go.kr` · `VwsmTrdarFlpopQq` (상권분석서비스 길단위인구) | `tot_flpop_co`, 시간대·연령대·요일별 유동인구 | 상권, 분기 |

| E | `{"lat":37.4979, "lng":127.0276, "industry":"미용실"}` | **93점인데 B** · 생존 확률 없음 · `evidence_weight` 0.4 | 음식점이 아닌 업종. 점수가 높아도 근거가 부족하면 등급은 최대 B다 |
| F | `{"lat":37.5663, "lng":126.9779, "industry":"우주정거장"}` | 점수 48 · **등급 `null`** · `evidence_weight` 0.15 · 업종 `unknown` | 업종 목록에 없는 이름은 `400` 오류가 아니라 "업종 미확정"으로 처리한다. 근거가 30% 미만이면 등급을 매기지 않는다. 업종 이름은 `/v1/industries?q=`로 먼저 찾는다 |
| G | A와 같은 위치에 `"industry":"카페", "radius_m":100` | 경쟁 강도 **0점** (100m 안 카페 4곳 / 전체 45곳, 입지계수 2.17) · 종합 39점 D | 반경을 바꾸면 경쟁 지표가 달라진다. 좁은 반경에서는 몇 곳 차이로도 크게 움직인다 |
| H | A에서 `biz_no`만 국세청에 등록되지 않은 번호로 | 평가는 정상 진행 · `business_check.status: "unknown"`, `tax_type: null` | 사업자번호 문제로 평가가 실패하지는 않는다 |

### 5-2. 이런 값은 받지 않는다 (바로 오류)

요청 단계에서 막히고 평가가 만들어지지 않는다. 오류 메시지는 `detail`에 한국어로 온다.

| 입력 | 응답 | `detail` |
|---|---|---|
| 위치 없이 `{"industry":"카페"}` | `400` | 위치가 필요합니다: lat+lng 또는 address 중 하나를 보내십시오 |
| `lat`만 보냄 `{"lat":37.5}` | `400` | lat과 lng는 함께 보내야 합니다 |
| 국외 좌표 `{"lat":40.7, "lng":-74.0}` | `400` | 위도(lat)는 33~39 사이 숫자여야 합니다 (대한민국 범위) |
| 반경 `{"radius_m":200}` | `400` | 반경(radius_m)은 100, 300, 500, 1000 중 하나입니다 |
| 사업자번호 하이픈 `{"biz_no":"124-81-00998"}` | `400` | 사업자번호(biz_no)는 하이픈 없이 숫자 10자리입니다 |
| 면적 `{"floor_area_m2":0}` | `400` | 매장 면적(floor_area_m2)은 1~100000 사이 숫자(㎡)여야 합니다 |
| GIF 이미지 | `400` | JPG/PNG/WebP만 받습니다 |
| 이미지 5장 | `400` | 이미지는 최대 4장입니다 |
| 6MB 이미지 | `413` | 이미지는 장당 5MB 이하만 받습니다 |

### 5-3. 접수는 되지만 실패로 끝나는 값

형식은 맞아서 `202`로 접수되지만, 위치를 확정하지 못해 `status: "failed"`로 끝난다. 사유는 `error`에 있다.

| 입력 | 결과 `error` |
|---|---|
| 없는 주소 `{"address":"서울 없는로 99999"}` | `422` 주소를 찾을 수 없음 — 지오코딩 결과가 없습니다 |
| 좌표는 서울, 주소는 부산 | `422` 좌표와 주소가 다름 — 좌표와 주소 위치가 332,238m 떨어져 있습니다 (허용 500m) |

### 5-4. 그 밖의 호출

| 호출 | 응답 |
|---|---|
| 없는 `assessment_id` 조회 | `404` 평가 없음 |
| 분석이 끝나기 전에 `/report` 또는 `/messages` | `409` 아직 분석 중 |
| `/report?format=pdf` | `501` PDF 준비 중 — html 리포트를 인쇄해 PDF로 저장 |
| `/messages`에 빈 질문 `{"message":""}` | `400` message는 1~4000자 문자열이어야 합니다 |
| `/v1/industries?q=치킨` | `I21006 치킨` (생존 모델 대상 `true`) |
| `/v1/coverage?lat=35.1587&lng=129.1604` (부산) | `coverage: national` — 항목별로 제공 여부와 준비 중 안내 |

## 8. 오류 코드

| 코드 | 언제 | 할 일 |
|---|---|---|
| `400` | 필수 항목 누락, 형식 오류, 이미지 형식·개수 오류 | `detail`에 적힌 항목을 고친다 |
| `401` | API 키가 없거나 틀림 | `X-API-Key` 확인 |
| `404` | 없는 `assessment_id` | 번호 확인 |
| `409` | 분석이 끝나기 전에 리포트·대화 요청 | `?wait=60`으로 완료를 기다린다 |
| `413` | 이미지가 5MB 초과 | 이미지를 줄인다 (긴 변 1568px 권장) |
| `422` | 주소를 찾을 수 없음, 좌표와 주소가 500m 이상 차이 | 주소나 좌표를 확인한다 |
| `501` | PDF 리포트 요청 | HTML을 인쇄한다 |
| `503` | AI 기능이 꺼져 있음 (대화) | 운영자에게 문의 |

오류 본문은 [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) 형식이다: `{ "title", "status", "detail", "instance" }`.

평가 자체가 실패하면 HTTP는 `200`이고 `status`가 `failed`로 온다. 사유는 `error`에 들어 있다.
